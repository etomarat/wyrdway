# Wyrdway — roadmap v0.3 (release-first)

Обновлено: 2026-03-14

Этот документ больше не пытается честно расписать весь проект на M2–M4 в ширину.
Его цель сейчас проще: зафиксировать, **что уже есть**, **сколько осталось code budget**
и **какой следующий релиз даёт самый заметный прирост геймплея**.

## 1) As-is по коду

- **M1:** базовая петля закрыта.
  `GARAGE -> REGION_MAP -> DRIVE -> POI -> DRIVE(return) -> RESULT -> GARAGE`
- **M1.5 / M1.6:** drive model, camera, drift readability и feel уже хорошо вложены в проект.
- **M1.7:** подписанный лут, outbound/return и базовый ремонт в гараже уже есть.
- **M1.8:** return chase с преследователем уже есть и сейчас является главным отличителем билда.
- **POI:** пока это компактный экран решения с таймером и наградой.
- **REGION MAP:** пока это список из 5 узлов без реальной ветвистости.
- **GARAGE:** пока это repair + заглушка upgrades.

## 2) Code budget

Локальный факт на 2026-03-14:

- `tic80/python/build.py` = `705631` байт
- `tic80/python/build.min.py` = `308009` байт

Практический лимит TIC-80 по исходнику: **512 KB source**.
Это значит, что после минификации у проекта остаётся примерно **204 KB сырого запаса**.

Вывод:

- у нас **уже больше половины лимита занято**;
- полноценные версии сразу трёх больших систем (`loot`, `map graph`, `garage sim`) в один заход рискованны;
- следующий шаг надо брать такой, который:
  - даёт видимый новый геймплей в релизе;
  - переиспользует уже существующие сцены и state;
  - не плодит широкую матрицу новых сущностей/UI.

## 3) Продуктовое решение на ближайший релиз

### Что считать P0

**Следующий релиз строим вокруг двух вещей:**

1. **Route map v1**
2. **Garage upgrades v1**

Это даёт игроку:

- осмысленный выбор **до заезда**;
- разный характер поездок **при том же core loop**;
- долгосрочный payoff после возврата в гараж.

### Что не делать P0

Пока сознательно **не** делаем:

- широкий loot-layer;
- grid / trunk / перенос предметов по слотам;
- глубокое обслуживание машины по деталям;
- отдельный boss-scene или сложных боссов;
- большую генерацию региона на 10–20 узлов.

Причина простая: всё это дорого по коду, UI и данным, а немедленный релизный эффект слабее,
чем у route choices + upgrades.

## 4) Что делать с тремя “большими кусками”

### 4.1 Лутинг

Решение: **сжать scope**.

- Сейчас лут = награды сегмента.
- В следующем релизе лут остаётся **компактным reward-layer**, а не отдельной системой инвентаря.
- Разрешённый объём:
  - `scrap`
  - `fuel`
  - опционально 1 новый тип награды, только если он сразу обслуживает карту или апгрейды

Не делаем сейчас:

- десятки предметов;
- контейнерный лут;
- отдельные запчасти;
- физический cargo management.

### 4.2 Карта / направления / развилки / боссы / модификаторы

Решение: **делать первой**.

Это лучший кандидат на ближайший релиз, потому что:

- меняет decision-making уже на старте каждой вылазки;
- переиспользует текущие `RunState`, `SegmentPlan`, `RoutePlanner`, `DriveScene`;
- позволяет добавить вариативность без новой тяжёлой сцены.

Целевой объём на v1:

- сегментная карта, которая читается **снизу вверх**;
- по **3 точки в ряд** с ограниченными связями между рядами;
- все пути внутри сегмента сходятся к боссу;
- обычные маршруты дают только `scrap/fuel`;
- длина сегментов растёт как `3 -> 4 -> 5`, дальше рост можно замедлять;
- весь run при этом остаётся **бесконечной цепочкой сегментов до провала**.

Что считать “боссом” на этом этапе:

- не отдельную битву;
- а **отдельный boss-POI** как вершину сегмента.

То есть “boss” на этом этапе уже не обычный route modifier, а специальная кульминационная точка сегмента,
но всё ещё без отдельной сложной боевой сцены.

### 4.3 Апгрейды и гараж

Решение: **делать сразу после route map**.

Но scope тоже режем:

- первый рабочий boss pool из 6 апгрейдов;
- новый апгрейд даётся сразу как `Level 1`;
- следующие уровни приходят чертежом и открываются в гараже за `scrap`;
- каждый апгрейд меняет уже существующие числа/правила.

Примеры допустимого уровня:

- больше max fuel;
- эффективнее repair;
- больше scrap reward;
- больше fuel reward;
- выше общая выживаемость.

Не делаем сейчас:

- слоты модулей;
- install/remove flow;
- экран обслуживания по деталям;
- большой гаражный UI с вкладками.

## 5) Порядок работ

### P0 — следующий публичный билд

1. **Route map v1**
   - вместо списка узлов сделать сегментную карту;
   - сохранить движение по рядам `3 -> 4 -> 5` и сход к боссу;
   - показать тип остановки и награды на карте;
   - сохранить выбранный путь в `SegmentPlan`.

2. **Garage upgrades v1**
   - 6 стартовых boss-upgrades;
   - `Level 1` выдаётся сразу, `Level 2+` открываются за `scrap`;
   - сохранить уровни в `Profile`;
   - применить в route reward / fuel / repair / survivability.

3. **Release prep**
   - обновить текст билда;
   - собрать changelog;
   - выкатить новую версию как “route + upgrades update”.

### P1 — только если останется бюджет

- 1 новый тип награды, который поддерживает апгрейды;
- 1 special variation поверх boss-POI;
- 1 дополнительный poi-type effect в логике награды/таймера.

### P2 — после релиза

- расширение loot-layer;
- глубокий garage interaction;
- bosses как отдельные encounters;
- более длинный региональный граф.

## 6) Что делать прямо сейчас

Если нужен **один следующий инженерный шаг**, то он такой:

1. зафиксировать новый shape данных для сегментной карты в `RunState` / `RoutePlanner`;
2. переписать `RegionMapScene` с 5-строчного списка на сегментную схему;
3. после этого решать, какие route distinctions реально нужны в коде первой версии, а какие можно оставить только на уровне карты и награды.

Это лучший старт, потому что после него сразу видно:

- влезает ли route-layer в code budget;
- достаточно ли этого для “ощутимо нового билда”;
- какие апгрейды реально нужны, а какие можно не делать.

## 7) Краткий критерий успеха следующего релиза

Релиз успешен, если игрок после 2–3 забегов может сказать:

- “Я **выбираю**, какой заезд брать, а не просто жму в список”
- “Машина **развивается** между заездами”
- “Поездки **ощущаются разными**, даже без нового большого контентного слоя”
